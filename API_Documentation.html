API 文件

AI 代理與 PowerShell 透過這些端點讀寫執行中的 Power BI Desktop 模型。

39 個 API 端點 支援同時操作多個 Power BI 所有 /api/* 需 X-API-Key 只接受 localhost:5500 連線

這是通用工具：先選定要操作哪一個 Power BI

一台機器可以同時開好幾個 Power BI Desktop，每一個都有自己的 msmdsrv 子行程與連接埠。 本服務不綁定任何特定檔案 —— 所有路徑都在每次請求時從執行中的行程即時推導 （msmdsrv.ParentProcessId → PBIDesktop → 命令列 → 開啟的檔案）。

請求用 X-PBI-Target 標頭指定目標，值可以是 Port 數字或檔名／路徑片段：

  • 只有一個實例 → 可以不帶，自動採用
  • 多個實例卻沒指定 → 一律回 400 並列出清單，連讀取也拒絕。猜錯的代價是改到別的模型，所以寧可回錯誤也不預設挑一個
  • 片段同時符合多個 → 回 400，要求改用 Port 精確指定

HTTP 標頭只能放 ASCII，中文檔名不能直接當標頭值 —— Use-PbiInstance 內部一律換算成 Port 再送出， 並記住完整路徑，PBI 關掉重開（Port 會變）時自動重新解析。

回應的欄位名稱一律是 camelCase（rows、truncated、elapsedMs…）；請求的參數名稱不分大小寫。

開始之前，兩件必須知道的事

1. 寫入只進記憶體，不會自動存檔。 TOM 的 SaveChanges() 只改 Power BI Desktop 記憶體中的模型。要落到 .pbix／.pbip 必須呼叫 /api/save。fileChanged 只代表「有檔案被寫了」；PBIP 請帶 Expect， 確認 expectFound 為 true 才算剛寫的內容真的進了磁碟。

2. 結構性變更後必須重算，否則查不到資料。 只寫量值不用重算；但建立計算表、關聯線、計算項目之後，不跑 /api/refresh 查詢就會回「需要重新計算，因此未包含任何資料」。

做了什麼要跑什麼耗時
建立計算表／計算項目refresh（指定該表）秒級
建立或修改關聯線／計算資料行refresh + RefreshType: "calculate"秒級
M 腳本（使用者在 Power Query 編輯器「關閉並套用」）不用 —— Power BI 會自己重整—
M 腳本（用 /api/update-m 寫入，Desktop 沒有出現套用提示）refresh（指定該表，full）看資料源
M 多輸出了新欄位先 add-column（給 SourceColumn），再 refresh 該表看資料源

貳查詢引擎

POST · 唯讀，寫完量值用來驗算
POST

/api/query

唯讀 DAX 查詢

查詢必須以 EVALUATE 或 DEFINE 開頭（唯讀防護，擋掉會變更模型的 XMLA 命令）。回傳欄位清單、列數、是否截斷，以及 elapsedMs。

回傳列數由伺服器封頂：逐列明細 50 列、彙總結果 300 列，MaxRows 只能調低。 truncated: true 代表還有資料沒帶回來，要總數請用 COUNTROWS。

DAX 語法錯誤回 400，body 含引擎的訊息與錯誤位置，可直接據此修正公式。查詢碰到受限欄位時，訊息裡引用的資料內容會換成 ‹已遮蔽›。

{ "Query": "EVALUATE ...", "MaxRows": 50, "TimeoutSeconds": 60, "AskUser": false } 資料保護（伺服器端強制）：每個欄位有一個等級（見第拾部）。只能計數的欄位只准出現在計數類函式內（DISTINCTCOUNT／COUNTROWS…）；只能彙總的欄位必須包在聚合函式內，或寫在篩選條件裡；換成代號的欄位可以當分組鍵，回傳的值是穩定代號 ID_3FA2B81C07（回應的 pseudonymized 會列出是哪些欄位）。量值、計算資料行、計算表與計算群組的定義會展開一起檢查。違者回 403。 AskUser: true：這句查詢被擋下時，在使用者的螢幕跳確認視窗，由他決定要不要放行這一次（最多 MaxRows 列，沒給就是逐列明細的上限，封頂 1000）。放行後的回應 approvedByUser 為 true、內容沒有經過遮蔽（每格最多 200 個字，超過會截斷）。沒被擋的查詢不會跳視窗。 被擋下的 403 回應有 reason（為什麼）、hint（怎麼改寫）、verdict（判定代碼）與 canAskUser。canAskUser: false 的情況不會跳視窗：寫法本身被禁（BLOCKED-FUNC）、模型定義讀不完整（BLOCKED-LOAD／BLOCKED-INCOMPLETE）、保護設定檔讀不出來（BLOCKED-SETTINGS），或查詢碰到超過 12 個受限欄位、去掉註解後超過 700 個字（視窗列不完）。使用者同意的是視窗裡那一句連同當時的量值定義 —— 按「是」之後定義有變會回 BLOCKED-CHANGED。
POST

/api/dmv

系統檢視查詢

執行 $SYSTEM DMV，用於查中繼資料、儲存統計與記憶體佔用。這些檢視只含中繼資料與統計，不會回傳事實資料列。

格式必須是單一來源的 SELECT <欄位或 *> FROM $SYSTEM.<檢視> [WHERE … | ORDER BY …]：開頭的註解、第二個 $SYSTEM 或第二個 FROM（子查詢、JOIN）都會被拒絕。

SELECT DIMENSION_NAME, COLUMN_ID, USED_SIZE FROM $SYSTEM.DISCOVER_STORAGE_TABLE_COLUMN_SEGMENTS 資料保護啟用時是白名單制：只開放模型的中繼資料與儲存統計（TMSCHEMA_TABLES／COLUMNS／MEASURES／RELATIONSHIPS…、DISCOVER_STORAGE_*、DISCOVER_OBJECT_MEMORY_USAGE）。其他檢視回 403 —— 有些會回傳欄位的每一個相異值（MDSCHEMA_MEMBERS）、M 腳本（TMSCHEMA_PARTITIONS）或別的連線跑過的查詢文字。回應的 allowed 會列出可以查的。相依性檢視（DISCOVER_CALC_DEPENDENCY）不在名單內，要查量值之間的引用請讀 /api/schema 的定義。

/api/restore

從快照還原

還原量值、計算資料行、關聯線、M 腳本、共用運算式。支援 DryRun 先看差異清單。

還原不是合併，是回到當時的狀態 —— 快照中不存在的量值與關聯會被刪掉。另外它不會刪除表格與角色，也不改模型層級屬性；沒被涵蓋的項目會列在回應的 uncovered 裡，別忽略。 預設範圍包含 M 腳本。還原 M 和直接寫 M 一樣：資料保護啟用時會先跳確認視窗，寫入後還要讓它生效並確認留下的版本（見第捌部）—— 只想還原量值請明確給 Scope: ["measures"]。 只在目標模型自己的快照資料夾裡找檔案，路徑分隔字元一律拒絕 —— 結構上就不可能把 A 模型的快照還原到 B 模型。 { "File": "20260805_121110__before.json", "DryRun": true, "Scope": ["measures"] }

POST

/api/refresh

重新整理資料

不指定 TableName 就是整個模型。RefreshType 可用 full／calculate／dataOnly／automatic／add／clearValues／defragment。

calculate 只重算 DAX、不重抓資料源，很便宜 —— 結構性變更後直接跑一次就好。

{ "TableName": "銷售", "RefreshType": "calculate" } 跑完才回應：message 是「已完成」，elapsedMs 是實際耗時 —— 收到回應就可以直接驗算。失敗會是錯誤回應。
POST

/api/save

模擬 Ctrl+S 存檔並驗證

把目標那一個 PBI Desktop 帶到前景送出 Ctrl+S，然後輪詢到檔案寫完為止（WaitSeconds 是上限，預設 30；寫完就提早回應）。

驗證範圍只有該實例自己的檔案：.pbix 看那一個檔；.pbip 看它的 .Report 與 .SemanticModel 兩個資料夾（照 .pbip 與 definition.pbir 裡的指標找）。旁邊不相干的檔案被寫入不會被當成存檔成功。

{ "WaitSeconds": 30, "Expect": ["銷售總額"] } { "VerifyOnly": true, "Expect": ["銷售總額"] } // 不送按鍵，只看磁碟

回應：fileChanged（有沒有檔案被寫）、changedFiles（哪些檔）、expectFound（Expect 指定的文字在不在磁碟上，僅 PBIP）。

fileChanged = true 不是「存到了」的證據 —— 遇過檔案有寫、但剛改的內容不在裡面。PBIP 請帶 Expect 看 expectFound。沒存到時最多重試一次，不要連續重送（跨行程送按鍵連按會被防毒視為可疑）；要確認就用 VerifyOnly。會短暫搶走鍵盤焦點 —— 這是 SendKeys 的固有限制。

POST

/api/update-m

覆寫資料表的 M 腳本

讀 M 請用 GET /api/schema 的 MQuery 欄位（PowerShell：Get-PbiMQuery / Set-PbiMQuery）。

資料保護啟用時，這個請求會先在使用者的螢幕跳確認視窗，他按「是」才執行。 { "TableName": "訂單", "Expression": "let ... in ..." } 只改模型那一份，而且寫入本身不會重抓資料：Power BI Desktop 的 Power Query 文件與 TOM 模型是兩份獨立的東西。寫入後 Desktop 的反應有兩種，兩種都遇過 —— 顯示「查詢中有暫止的變更尚未套用」（由使用者按「套用」），或完全沒有提示（對該表跑 /api/refresh，新的 M 才會套用到資料上）。兩份內容不同時，套用有可能以 Desktop 那份為準，所以生效後務必確認留下的是這次寫入的版本。
另一條路：把完整的 let...in 交給使用者，請他在 Power Query 編輯器的進階編輯器貼上，再「關閉並套用」。

計算群組

時間智慧的殺手鐧：一組計算項目就能讓所有量值支援 YTD／MTD／YoY，不必為每個量值手寫衍生版本。

玖批次

效能與交易語意
POST

/api/batch

一次連線、一次 SaveChanges

寫 20 個量值 = 20 次 HTTP + 20 次 SaveChanges() + 20 次模型重算。批次只重算一次。

更關鍵的是失敗語意：預設 StopOnError: true 且最後才存檔 —— 任一步失敗，整批變更全部丟棄，模型維持原狀。只有在後續操作依賴前面結果「已生效」時才需要 SavePerOp: true（此時失敗不會回滾，回應會明確告訴你前幾個已經寫進去了）。

單次上限 200 個操作。支援 DryRun。

{ "Operations": [ { "Op": "upsert-measure", "Args": { "TableName": "量值", "MeasureName": "銷售總額", "Expression": "SUM(f[Amount])", "FormatString": "#,0" } }, { "Op": "upsert-measure", "Args": { "TableName": "量值", "MeasureName": "訂單數", "Expression": "COUNTROWS(f)" } } ], "StopOnError": true }

可用的 Op： upsert-measure、delete-measure、move-measure、 add-column、delete-column、set-column-props、 create-table、delete-table、 rename、upsert-relationship、delete-relationship、 upsert-calc-group、upsert-calc-item、delete-calc-item、 upsert-role、delete-role、upsert-expression、 delete-expression、set-model-props、update-m

update-m 也可以放進批次。批次裡有任何會動到 Power Query 的操作時，資料保護啟用下會先跳一次確認視窗（列出全部，一次最多 8 項）；寫完一樣要讓它生效並確認留下的版本（見第捌部）。

每個欄位的內容 AI 能看到多少 · 由使用者決定
GET

/api/protection

每個欄位的保護等級

逐表、逐欄回傳 level（open 開放／pseudonym 換成代號／countOnly 只能計數／aggregateOnly 只能彙總）、 source（explicit 使用者逐欄設定／pattern 通用規則／default 預設開放）與符合的樣式 rule。 另有 enabled、configured（存過至少一筆逐欄設定）、savedAt、limits（列數上限）、summary、 pathKnown（服務知不知道檔案路徑）、canSave（認不認得出這份模型、設定存不存得起來）、 inheritedFrom（設定是靠內容認回來的時候，當初儲存它的檔案）、stale（對不到現有欄位的設定）。

等級是結構資訊，AI 可以放心讀 —— 先知道哪些欄位受限，才寫得出一次就過的查詢。

PowerShell：Get-PbiProtection [-Table 表] [-All] [-Raw] 等級怎麼決定：逐欄設定 ＞ 通用規則 ＞ 開放。通用規則是 appsettings.json 的 DataProtection 清單（欄名樣式，對每個模型都生效）。逐欄設定每個模型一份，存在 %LOCALAPPDATA%\PBI_AI_Bridge\protection\，只由服務讀寫。設定跟著模型走：先比完整路徑，對不上就靠資料行的固定代號（LineageTag）認 —— 檔案搬家、改名、另存新檔，或從 Power BI 裡面開啟（拿不到路徑）時設定都還在。靠內容認回來的設定只套用到認得出來的同一個資料行。
POST放寬要使用者確認

/api/protection

變更欄位的保護等級

收緊（開放 → 受限、任何等級 → 只能計數）立刻生效。只要有任何一欄變寬鬆，服務就在使用者的螢幕跳出 Windows 確認視窗、列出每一欄的變更，他按「是」才套用；否則整批不套用並回 403。一次最多放寬 12 欄（視窗要列得完）。

{ "Changes": [ { "Table": "客戶", "Column": "電話", "Level": "countOnly" }, { "Table": "客戶", "Column": "客戶名稱", "Level": "pseudonym" } ] }

Level: "default" 拿掉逐欄設定、回到通用規則；{ "Reset": true } 清除這個模型全部的逐欄設定（有任何一欄因此變寬鬆，或設定檔讀不出來時，會跳確認視窗；不受 12 欄的限制）。文字欄位不能設成 aggregateOnly。

把一個本來就開放、也沒有逐欄設定的欄位設成 open 不會存任何東西（回「沒有需要變更的項目」）。等待確認的期間設定被別的請求改過時回 409、這一批不套用 —— 重新讀取後再送。

PowerShell：Set-PbiProtection -Table 客戶 -Column 電話, 地址 -Level countOnly 人平常在儀表板的「資料保護」分頁用點的。儀表板會把一次儲存拆成兩次送：先送收緊、再送放寬 —— 錯過確認視窗時，收緊的部分已經生效。
確認視窗AI 繞不過去

請使用者本人確認

三種情況服務會自己跳出 Windows 確認視窗

情況觸發的請求視窗會列出
放寬欄位等級POST /api/protection（有任何一欄變寬鬆 —— 包含 Reset 造成的；或設定檔讀不出來時的重設）每一欄從什麼等級變成什麼等級
放行一句被擋下的查詢POST /api/query 帶 AskUser: true被擋的原因、查詢提到的受限欄位、最多幾列、查詢內容
經由 API 改寫 Power Queryupdate-m、upsert-expression、create-table（Kind: "m"）、add-column（給 SourceColumn）、restore（範圍含 mquery／expressions）、含上述操作的 batch要改哪些表／共用查詢（一次最多 8 項）

為什麼需要：儀表板與 AI 用的是同一把金鑰，只靠金鑰的話 AI 可以自己放寬保護。視窗是服務行程自己畫的，內容由伺服器決定，按鈕只有坐在電腦前的人按得到。Power Query 也要確認，是因為 M 可以把受限欄位的內容搬進開放的欄位，而查詢掃描看不懂 M。

預設按鈕是「否」；120 秒沒回答當成否；被拒絕之後 30 秒內不再詢問；同一時間只會有一個視窗。請求會等到使用者回答才回應。沒獲得同意時回 403：

{ "error": "⛔ …", "reason": "你在確認視窗選了「否」。…", "answer": "No", // No / Timeout / Busy / CoolingDown / Unavailable "retryAfterSeconds": 30 } 給 AI 代理：會跳視窗的動作，送出之前先在對話裡向使用者說明；被拒絕之後不要連續重送，也不要換個寫法再試。資料保護未啟用（DataProtection:Enabled = false）時，Power Query 的寫入不會跳視窗。
